# Архитектура BARS

## 1. Общая картина

```text
┌──────────────────────────────────────────────────────────────┐
│ Браузер                                                      │
│                                                              │
│  UI (vanilla JS)                                             │
│    │                                                         │
│  services/  ── Supabase JS ──────────────┐                   │
│    │                                    │                   │
│  crypto/  (WebCrypto + @hpke/core)       │                   │
│    │                                    │                   │
│  IndexedDB: неэкстрагируемый P-256 ключ  │                   │
└─────────────────────────────────────────┼───────────────────┘
                                          │ HTTPS / WSS
                                          ▼
┌──────────────────────────────────────────────────────────────┐
│ Supabase                                                     │
│                                                              │
│  Auth ──► auth.users ──trigger──► public.profiles            │
│                                                              │
│  Postgres                                                    │
│    conversations, conversation_members                       │
│    devices            (ключи, status active/pending/revoked)  │
│    device_sessions    (JWT session_id → device)              │
│    messages           (ciphertext + AAD-параметры)           │
│    message_keys       (HPKE-конверты на устройства)          │
│    access_invites     (только Dashboard/service role)        │
│    key_backups        (зашифрованный recovery kit)           │
│                                                              │
│  RPC (security definer): регистрация/одобрение устройства,   │
│  recovery, отзыв устройства/сессии, профиль, общий чат,      │
│  личные диалоги и контакты, отправка сообщения               │
│                                                              │
│  Realtime: Postgres Changes на messages, RLS применяется     │
└──────────────────────────────────────────────────────────────┘
```

Клиент не имеет прямых `INSERT`/`UPDATE`/`DELETE` на доменные таблицы. Единственные клиентские записи — `key_backups` с зашифрованным recovery kit. Всё остальное — только чтение под RLS и вызовы RPC.

## 2. Ключи и идентичность устройства

### 2.1. Ключ устройства

При первом входе на устройстве:

1. `crypto.subtle.generateKey({ name: 'ECDH', namedCurve: 'P-256' }, false, ['deriveBits'])`.
2. Публичный ключ экспортируется в JWK (`kty`, `crv`, `x`, `y`) и регистрируется через RPC `register_device`.
3. Приватный ключ остаётся `CryptoKey` с `extractable: false` и сохраняется в IndexedDB вместе с `deviceId`, `userId`, именем устройства и публичным JWK.

`register_device` одновременно привязывает текущий Supabase JWT (`session_id`) к строке устройства в `device_sessions`. Без активной привязки `is_active_user()` возвращает `false`, поэтому RLS и все остальные RPC закрыты. Первое устройство аккаунта становится `active`; каждое следующее — `pending`, пока его не одобрит активное устройство через `approve_device`.

При повторном входе клиент читает локальную идентичность и сверяет публичный ключ с сервером. Если сервер сообщает, что устройство отозвано, клиент показывает экран «Устройство отозвано» и не создаёт новую пару автоматически. Если ключ не совпал или устройство исчезло из базы, локальная запись удаляется, создаётся новая пара, а сессия привязывается к новому устройству. Если сессия уже была привязана к другому устройству, сервер возвращает `session_device_mismatch`, и клиент предлагает выйти и войти заново.

> Важно: HPKE всегда получает **пару** `{ privateKey, publicKey }`. Библиотека `@hpke/core` умеет выводить публичный ключ из приватного, но для неэкстрагируемого P-256 ключа теряет знак y-координаты. Передача готового публичного ключа устраняет эту проблему и сохраняет non-extractable свойство.

### 2.2. Несколько устройств

У каждого устройства своя пара и своя строка в `devices`. Активные устройства получают конверт ключа для каждого нового сообщения. Pending-устройства:

- привязаны к своей сессии, но `is_active_user()` для них возвращает `false`;
- не получают новые конверты и не видны участникам диалога в `get_conversation_devices`;
- могут читать только собственный профиль и собственную строку устройства, чтобы клиент мог опрашивать статус;
- становятся активными только после `approve_device` с уже активного устройства.

Отозванные устройства:

- не получают новые конверты;
- остаются в таблице, чтобы можно было проверить старые подписи/ключи отправителей;
- могут читать только те старые сообщения, конверты для которых уже были им выданы;
- все их сессии в `device_sessions` помечаются `revoked_at`, поэтому JWT перестаёт работать немедленно.

### 2.3. Привязка сессии

Supabase JWT содержит claim `session_id`, уникальный для каждого входа. Схема:

```text
device_sessions(
  session_id uuid primary key,
  user_id uuid → profiles,
  device_id uuid → devices,
  created_at, last_seen_at, revoked_at
)
```

Правила:

- одна сессия — одно устройство; повторный `register_device` с тем же `session_id` и другим `device_id` отклоняется (`session_device_mismatch`);
- `register_device` требует активный профиль, но не требует привязки — иначе первую сессию нечем было бы связать;
- новое устройство при уже существующих устройствах создаётся `pending`; его сессия привязывается, но не даёт доступа;
- `is_active_user()` требует одновременно активный профиль, активную привязку и активное устройство;
- `approve_device` переводит своё pending-устройство в `active` и записывает `approved_at`/`approved_by_device_id`;
- `revoke_device` отзывает активное устройство или отклоняет pending-запрос;
- `cancel_device_request` позволяет pending-устройству отменить собственный запрос;
- `revoke_session` вызывается клиентом при локальном выходе и отзывает только текущую сессию.

Остаточный риск: украденный пароль позволяет создать до трёх pending-запросов. Прочитать переписку такое устройство не может, но может создавать шум и мешать подключению легитимного устройства. Если у пользователя не осталось активных устройств, одобрять запрос некому — владелец открывает короткое reset-окно через SQL.

### 2.4. Recovery kit

Recovery-ключ — пользовательская P-256 пара, которая живёт как специальная строка `devices` с `kind = 'recovery'`. Она получает HPKE-конверты наравне с браузерными устройствами, но не участвует в `device_sessions` и не может отправлять сообщения. Публичный ключ recovery-строки неизменяем на месте: замена требует отзыва старого ключа и создания нового kit, чтобы украденная сессия не могла незаметно перенаправить будущие конверты.

```text
создание:
  generateRecoveryKeys() → { publicJwk, privateJwk }
  secret  = { v: 1, userId, deviceId, publicJwk, privateJwk }
  key     = PBKDF2-SHA256(passphrase, salt, 600000)
  backup  = AES-256-GCM(key, iv, JSON(secret), aad="bars:v1:recovery:<userId>")
  server  ← key_backups(version, kdf, iterations, salt, iv, ciphertext)
  файл    ← { v, userId, kdf, kdfIterations, salt, iv, ciphertext }

восстановление:
  расшифровать backup локально
  сверить deviceId/publicJwk с активной recovery-строкой
  импортировать privateJwk как non-extractable CryptoKey
```

Парольная фраза нигде не сохраняется. На сервере нет ни её, ни приватного ключа. Recovery-ключ не покрывает сообщения, отправленные до его создания.

### 2.5. Подтверждение нового устройства

```text
новое устройство                    активное устройство
     │                                      │
     │ register_device → pending            │
     │ сессия привязана, доступа нет         │
     │                                      │
     │ код = SHA-256(public JWK) → ABCD-…    │
     │                                      │
     │             пользователь сверяет коды│
     │                                      │
     │                      approve_device  │
     │ ←──────────── active ────────────────│
     │                                      │
     │ is_active_user() = true              │
```

Правила:

- первое устройство аккаунта сразу `active`;
- при наличии device-строк новое устройство создаётся `pending`;
- лимит — 20 активных устройств и 3 одновременных pending-запроса;
- одобрять и отклонять может только сессия, привязанная к активному устройству того же пользователя;
- `revoke_device` для pending работает как отказ, `cancel_device_request` — как отмена со стороны нового устройства;
- код-отпечаток считается из публичного ключа (`kty`, `crv`, `x`, `y`) и не является секретом; он нужен, чтобы пользователь не одобрил чужой запрос;
- ссылка `#/approve/<deviceId>` и QR содержат только публичный id устройства. Активное устройство перечитывает строку через `getDevice` под RLS, показывает тот же код и вызывает `approve_device`; ссылка не даёт прав и не заменяет сверку кода;
- при потере всех активных устройств владелец вручную отзывает устройства и открывает `profiles.device_reset_until = now() + interval '15 minutes'`; следующее новое устройство становится `active`, флаг очищается.

## 3. Конверт сообщения (BARS Envelope v1)

```text
contentKey = random 32 bytes
payload    = JSON { v: 1, kind: "text", text }
aad        = "bars:v1:message:<conversation>:<message>:<sender>:<senderDevice>:<type>"
ciphertext = AES-256-GCM(contentKey, iv, payload, aad)

для каждого активного устройства получателя:
  info    = "bars/v1/key:<message>:<device>"
  senderCtx = HPKE.Auth.SetupSender(recipientPublicKey, senderPrivateKey, info)
  enc       = senderCtx.enc
  wrapped   = senderCtx.Seal(contentKey, aad)
```

На сервере хранятся `ciphertext`, `iv`, `enc`, `wrapped_key`, `crypto_version`, но не `contentKey` и не текст.

Получатель:

1. Находит свой конверт по `device_id`.
2. Строит `aad` из публичных полей строки сообщения.
3. `HPKE.Auth.SetupRecipient(recipientKeyPair, enc, senderPublicKey, info)`.
4. Разворачивает `contentKey` и расшифровывает payload с тем же `aad`.

HPKE Auth даёт получателю уверенность, что конверт создал владелец приватного ключа отправителя. Подмена `sender_device_id`, `message.id`, диалога или типа ломает AAD и расшифровку.

`info` привязывает конверт к конкретному сообщению и устройству, поэтому переигровка конверта под другим `device_id` не проходит.

### Почему не одна общая группа ключей

M1 использует схему «случайный ключ на сообщение + отдельный конверт на устройство». Она проста, детерминирована и не требует общего состояния между устройствами. Для 3–5 человек и 5–20 устройств накладные расходы малы.

Это не Signal Double Ratchet и не MLS. Схема не даёт forward secrecy и post-compromise security; переход на MLS/Signal запланирован отдельным этапом. Формат `crypto_version` уже позволяет ввести новый конверт без изменения UI.

## 4. Отправка сообщения

```text
UI
 │ 1. оптимистично показывает сообщение (status=sending)
 ▼
encryptMessage()
 │ 2. получает активные устройства участников
 │ 3. генерирует contentKey, шифрует текст
 │ 4. заворачивает ключ для каждого устройства
 ▼
RPC send_message()
 │ 5. проверяет пользователя, членство, устройство, размеры, rate limit
 │ 6. одной транзакцией вставляет messages + message_keys
 │ 7. обновляет conversations.last_message_at
 ▼
Postgres commit
 │
 ├─ Realtime INSERT → остальные клиенты
 └─ ответ RPC → отправитель помечает сообщение sent
```

Идемпотентность: уникальная пара `(sender_id, client_message_id)`. Если ответ потерялся и клиент повторил запрос, RPC вернёт уже созданное сообщение, не создавая дубликат и не вставляя повторно конверты.

Все ключи из клиентского массива фильтруются на сервере: принимаются только активные устройства активных участников диалога, включая активный recovery-ключ. Если после фильтрации не осталось ни одного конверта, RPC завершается ошибкой `invalid_keys`. Клиент дополнительно не включает в конверты устройства заблокированных профилей. `recipient_kind` в `message_keys` выставляется триггером по `devices.kind`.

## 5. Получение и Realtime

Подписка — Postgres Changes:

```js
supabase
  .channel(`bars:messages:${conversationId}:${random}`)
  .on('postgres_changes', {
    event: 'INSERT',
    schema: 'public',
    table: 'messages',
    filter: `conversation_id=eq.${conversationId}`,
  }, handler)
```

Realtime проверяет RLS-политику `messages_select_members` и не отправляет строки чужих диалогов. Payload содержит только строку `messages`; клиент дозагружает сообщение с вложенными `message_keys` (под RLS видны только конверты текущего пользователя), расшифровывает и добавляет в состояние.

При переподключении клиент вызывает `syncLatest()` и добирает сообщения по `seq > последнего`. Это закрывает разрыв, пока сокет был недоступен.

История грузится страницами по 50 по убыванию `seq`; в памяти сортируется по возрастанию. Старые сообщения без конверта для текущего устройства показываются как «Зашифровано для другого устройства».

## 6. Схема данных

### profiles

Публичный профиль, создаётся триггером на `auth.users`. `status`: `pending | active | blocked`. `role`: `owner | member`. RLS: себя или участников общих диалогов, при условии, что текущий пользователь активен.

### access_invites

Закрытая регистрация. Политик для клиентов нет вообще. Приглашения создаются через Dashboard/SQL. Триггер при регистрации ищет неиспользованное приглашение по email; если оно есть — профиль сразу `active` и пользователь попадает в общий чат.

### conversations / conversation_members

`group` и `direct`. Общий чат имеет фиксированный UUID `00000000-0000-4000-8000-000000000001`. `ensure_default_conversation()` чинит членство при входе.

Личный диалог получает `direct_key = "<меньший uuid>:<больший uuid>"` и уникальный индекс по этому полю. `create_direct_conversation(peer_id)` идемпотентен: повторный вызов из любой стороны возвращает существующий диалог и при необходимости восстанавливает обе строки `conversation_members`. Создавать диалог можно только с активным пользователем, с которым уже есть общий разговор. `list_contacts()` возвращает активных собеседников из общего круга и id уже существующего личного диалога. RLS для `conversations`, `conversation_members`, `messages` и `devices` остаётся членством в диалоге, поэтому личные сообщения автоматически изолированы.

### devices

Публичные ключи и статус. Приватные ключи сюда не попадают. `id` генерируется клиентом (`crypto.randomUUID()`), что позволяет повторную регистрацию после перезагрузки без гонок. `status`: `active | pending | revoked`. `kind = 'device'` — браузер, `kind = 'recovery'` — пользовательский ключ восстановления; активный recovery-ключ может быть только один. Для аудита хранятся `approved_at` и `approved_by_device_id`. Отозванные строки не удаляются: на `sender_device_id` старых сообщений действует `ON DELETE RESTRICT`.

### device_sessions

Привязка `session_id` из JWT к устройству. Клиенты не имеют ни грантов, ни политик: таблицу читают и пишут только `security definer` функции. `revoked_at` завершает сессию немедленно, не дожидаясь истечения access token. Вспомогательная функция `current_session_id()` извлекает claim `session_id` из `auth.jwt()`.

### messages

Только шифротекст. `seq` — identity-колонка для стабильной пагинации и `syncLatest`. `unique(sender_id, client_message_id)` — идемпотентность.

### message_keys

Один конверт на устройство. `unique(message_id, device_id)`. RLS отдаёт пользователю только его конверты.

### key_backups

Зашифрованный recovery kit: соль, IV, шифротекст и параметры KDF. Парольная фраза и приватный ключ на сервер не попадают. RLS разрешает пользователю читать и обновлять только свою строку.

## 7. RPC и RLS

```text
current_session_id()             — session_id из auth.jwt()
is_active_profile()              — профиль current user active (только для register_device)
is_active_user()                 — профиль active + активная привязка сессии + активное устройство
shares_conversation(user_id)     — есть ли общий диалог
is_conversation_member(conv_id)  — участие в диалоге
```

Все — `security definer`, `stable`, с пустым `search_path`. `current_session_id()` и `is_active_profile()` доступны только владельцу схемы (вызываются из других definer-функций); остальные — только `authenticated`.

Политики чтения:

- `profiles` — свой профиль или профиль участника общего диалога;
- `conversations`, `conversation_members` — участникам;
- `devices` — свои или участников общего диалога;
- `messages` — участникам диалога;
- `message_keys` — только свои конверты;
- `key_backups` — только свои, плюс insert/update.

RPC:

- `register_device` — создать/обновить устройство, привязать текущий `session_id`; первое устройство `active`, следующие `pending`, лимит 20 активных и 3 pending;
- `approve_device` — одобрить своё pending-устройство с активной сессии;
- `cancel_device_request` — отменить собственный pending-запрос;
- `register_recovery_key` — создать/обновить один recovery-ключ пользователя (без сессии);
- `revoke_device` — отозвать своё активное устройство и все его сессии либо отклонить pending-запрос;
- `revoke_session` — отозвать только текущую сессию (локальный выход);
- `update_profile` — изменить отображаемое имя;
- `ensure_default_conversation` — membership общего чата;
- `list_contacts` — активные собеседники из общего круга и существующий личный диалог;
- `create_direct_conversation` — идемпотентно создать/вернуть личный диалог с активным участником общего круга;
- `get_conversation_devices` — публичные ключи устройств участников (pending исключены; отозванные остаются для проверки старой истории и статуса профиля);
- `send_message` — атомарная отправка.

`send_message` валидирует:

- активность пользователя и членство в диалоге;
- активность устройства-отправителя и принадлежность пользователю;
- тип (`text` в M1) и версию конверта (`1`);
- размеры ciphertext/IV и количество конвертов;
- rate limit: не более 20 сообщений за 10 секунд;
- что после фильтрации остался хотя бы один валидный конверт для активного устройства активного участника.

## 8. Frontend

- `src/app/app.js` — сессия, поколения загрузки (защита от гонок), маршруты, splash/login/access/pending/chat.
- `src/features/pending/pending-view.js` — экран ожидания одобрения, код-отпечаток, QR/ссылка, опрос статуса и отмена запроса.
- `src/features/approval/approval-view.js` — модалка одобрения по ссылке: перечитывает pending-устройство, показывает код и требует явное подтверждение.
- `src/features/chat/chat-view.js` — список диалогов, история, пагинация, optimistic send, ретраи, дешифровка, realtime, бейдж pending-запросов, настройки.
- `src/features/chat/new-dialog-view.js` — модалка «Новый диалог»: контакты из RPC, поиск, идемпотентное создание и открытие личного диалога.
- `src/features/settings/settings-view.js` — профиль, пароль, pending-запросы, устройства, отзыв, скрытые отозванные, recovery kit, выход.
- `src/services/*` — тонкая обёртка Supabase; никакой криптографии.
- `src/crypto/*` — ключи, HPKE, конверт, IndexedDB.
- `src/styles/*` — токены, glass, layout, views, responsive.

Маршруты hash-based, чтобы GitHub Pages не требовал SPA-fallback:

- `#/chat` — список диалогов (мобильный) / общий экран;
- `#/chat/<uuid>` — открытый диалог;
- `#/approve/<uuid>` — модалка одобрения устройства по ссылке.

На ширине ≤ 900px сайдбар и чат — отдельные экраны, чат выезжает поверх. На десктопе — двухпанельный layout. Высота приложения синхронизируется с `visualViewport`, чтобы клавиатура телефона не перекрывала поле ввода.

## 9. Точки расширения

| Возможность | Точка входа |
| --- | --- |
| Личные диалоги | реализовано: `direct_key`, `list_contacts`, `create_direct_conversation`, модалка «Новый диалог» |
| Непрочитанные и уведомления | счётчики по диалогам и push/локальные уведомления без текста |
| Стикеры | `messages.type = 'sticker'`, добавить `sticker_packs`/`stickers`, включить тип в RPC |
| Вложения | отдельная таблица метаданных + Supabase Storage с шифрованием на клиенте |
| Recovery kit | реализован: `key_backups`, `devices.kind = 'recovery'`, UI создания/восстановления |
| MLS/Signal | новый `crypto_version`, новые таблицы конвертов/сессий, старые сообщения читаются старым кодом |
| QR-сопряжение | реализовано: ссылка `#/approve/<deviceId>` + тот же `approve_device`; код-отпечаток сверяется вручную |
| Push | service worker + шифрованные payload'ы без текста |

Главное правило: сервер никогда не получает приватные ключи, content keys и открытый текст. Любая новая функция должна сохранять этот инвариант.
