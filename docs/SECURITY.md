# Безопасность BARS

Документ описывает модель угроз, криптографические инварианты и известные ограничения M1. Он не заменяет независимый аудит.

## 1. Что защищаем

| Актив | Где находится | Кто не должен получить |
| --- | --- | --- |
| Текст сообщений | только на устройствах участников | сервер, провайдер, посторонние |
| Content keys | только в памяти устройства | сервер, другие устройства |
| Приватные ключи устройств | IndexedDB, `extractable: false` | сервер, JS-код, другие пользователи |
| Пароль | Supabase Auth (хэш на сервере) | другие пользователи, клиентский код |
| Список участников и метаданные | Postgres | посторонние; сервер видит |

BARS не претендует на анонимность: сервер знает, кто с кем состоит в диалоге, когда и сколько сообщений отправлено, какие устройства у пользователя. Он не должен знать содержимое.

## 2. Модель угроз

### Защищает от

- Пассивного чтения базы и бэкапов Supabase.
- Компрометации сервера в модели **honest-but-curious**: сервер не может расшифровать содержимое сохранённых сообщений.
- Перехвата HTTPS-трафика без TLS-компрометации.
- Подмены сообщения или конверта при хранении/передаче: AAD и HPKE Auth ломаются.
- Подделки отправителя внешним клиентом без приватного ключа устройства отправителя.
- Повторного использования конверта под другим `device_id` или `message_id`.
- Чтения чужих диалогов через Supabase API: RLS и отсутствие write-грантов.
- Публичной регистрации: приглашения и `status = pending`.
- XSS через пользовательский текст: только `textContent`, статический HTML, CSP.

### Не защищает от

- **Вредоносного сервера/оператора с доступом к БД.** M1 не имеет key transparency и safety numbers. Сервер управляет каталогом публичных ключей и может подменить ключ устройства, а также напрямую вставить строку в `messages`. E2EE гарантирует конфиденциальность при честном сервере и целостность при честном каталоге ключей, но не даёт полноценной защиты от активного сервера. Проверка ключей вне канала — задача следующих версий.
- **Скомпрометированного устройства.** Пока страница открыта, XSS или вредоносное расширение может использовать неэкстрагируемый ключ для расшифровки и отправки. Non-extractable защищает от кражи ключа, но не от злоупотребления им в рантайме.
- **Компрометации GitHub Pages / цепочки поставки.** Клиентский код — доверенная база. Подмена JS на хостинге или в npm-зависимости обходит E2EE.
- **Потери всех устройств.** Нет recovery kit: старые сообщения восстановить нельзя.
- **Forward secrecy / post-compromise security.** Схема не ratchet-протокол. Компрометация устройства раскрывает все сообщения, для которых ему выдали конверт.
- **Метаданных.** Время, размеры, отправитель, состав диалога и устройства видны серверу.
- **DoS, блокировки аккаунта, отказа сервиса.**
- **Квантовых атак.** P-256 и AES-256 выбраны как практичный баланс; постквантовая миграция не реализована.

## 3. Криптографические инварианты

1. Приватный ключ устройства создаётся с `extractable: false` и никогда не сериализуется.
2. На сервер попадает только публичный JWK (`kty`, `crv`, `x`, `y`).
3. Для каждого сообщения генерируется новый 256-битный content key.
4. Content key заворачивается отдельно для каждого активного устройства получателя.
5. Для конвертов используется HPKE Auth, а не Base mode: получатель аутентифицирует отправителя.
6. AAD обязательно включает `conversation_id`, `message_id`, `sender_id`, `sender_device_id`, `type`.
7. `info` включает `message_id` и `device_id` получателя.
8. Один и тот же `(ciphertext, iv, wrapped_key)` не переиспользуется для другого сообщения.
9. Все ключи, кроме публичных, очищаются в памяти после использования (насколько это возможно в JS).
10. Сервер не принимает конверты для неучастников диалога и неактивных устройств.

### Параметры

| Параметр | Значение |
| --- | --- |
| KEM | DHKEM(P-256, HKDF-SHA256), RFC 9180 |
| KDF | HKDF-SHA256 |
| AEAD конверта | AES-256-GCM |
| Режим HPKE | Auth |
| Payload | AES-256-GCM, 256-bit key, 96-bit random IV, 128-bit tag |
| Версия | `crypto_version = 1` |
| Кодирование | base64 для ciphertext, iv, enc, wrapped_key |
| AAD | `bars:v1:message:<conversation>:<message>:<sender>:<senderDevice>:<type>` |
| info | `bars/v1/key:<message>:<device>` |

### Почему пара ключей обязательна

`@hpke/core` при передаче только приватного `CryptoKey` пытается вывести публичный ключ. Для неэкстрагируемого P-256 ключа библиотека восстанавливает y-координату и канонизирует её знак. Это совпадает с исходным публичным ключом только примерно в половине случаев и приводит к случайным отказам расшифровки. Поэтому `encryptMessage` и `decryptMessage` всегда передают HPKE объект `{ privateKey, publicKey }`. Это не ослабляет non-extractable свойство: публичный ключ и так публичен.

## 4. Идентичность и устройства

### Регистрация

Клиент генерирует `deviceId` и P-256 пару. RPC `register_device` проверяет:

- пользователь аутентифицирован и активен;
- JWK имеет `kty=EC`, `crv=P-256`, корректные по форме `x`/`y`;
- устройство принадлежит этому пользователю (при обновлении);
- активных устройств не больше 20.

Публичный ключ можно обновить только для своего активного устройства. Это позволяет повторную регистрацию после перезагрузки, но не даёт менять чужие устройства через API.

### Отзыв

`revoke_device` переводит устройство в `revoked`. Новые сообщения ему больше не шифруются. Устройство сохраняется для проверки старых ключей отправителей.

Честный клиент при следующей загрузке видит статус `revoked` и не регистрирует новую пару автоматически: он показывает экран «Устройство отозвано». Это защищает от случайного «воскрешения» отозванного браузера, но не является полной защитой: очистка данных сайта или украденная сессия позволяют зарегистрировать новое устройство.

**Ограничение M1:** отзыв не завершает сессию Supabase на этом устройстве. Злоумышленник с украденной сессией может очистить хранилище и зарегистрировать новое устройство. В M1.5 планируется: привязка сессии к устройству, завершение сессий, подтверждение нового устройства, лимит и журнал регистраций. До этого при компрометации нужно менять пароль, отзывать сессии в Supabase Dashboard и отзывать устройства.

### Несколько устройств

Каждое устройство получает свой конверт. Это даёт независимую расшифровку и позволяет отзывать устройства по одному. Цена — размер `message_keys`, растущий линейно от числа устройств.

## 5. Серверная модель

### RLS

- Клиенты `authenticated` имеют `SELECT` только на доменные таблицы.
- `access_invites` не имеет клиентских политик и грантов.
- Запись — только через `security definer` RPC.
- `send_message` принимает конверты только для активных устройств активных профилей. Заблокированный пользователь перестаёт получать новые ключи, даже если его устройство осталось в списке.
- `key_backups` — исключение: собственные строки можно создавать/обновлять (задел под recovery).
- Helper-функции имеют `search_path = ''` и execute только для `authenticated`.

### RPC

Security definer функции выполняются с правами владельца, поэтому самостоятельно проверяют `auth.uid()`, активность профиля, членство и принадлежность устройства. Нельзя полагаться только на RLS при записи.

### Realtime

Postgres Changes использует RLS. Клиент подписан на `messages` с фильтром по `conversation_id`, но фактическую авторизацию выполняет политика `messages_select_members`. `message_keys` в realtime-payload не входят; клиент догружает их отдельным запросом под своей RLS.

### Что видит сервер

- email и профиль;
- состав диалогов;
- устройства, их имена и публичные ключи;
- отправителя и устройство отправителя;
- время, порядок и размер сообщений;
- количество конвертов и их получателей;
- IP-адреса и User-Agent при запросах (стандартно для Supabase).

Сервер не видит текст, content key, приватные ключи и recovery-материал (которого пока нет).

## 6. Клиентская безопасность

- **CSP:** `default-src 'self'`, `script-src 'self'`, без inline-скриптов и `eval`. `style-src` разрешает inline-стили, потому что тема использует динамические CSS-переменные. `connect-src` ограничен Supabase HTTPS/WSS.
- **Никаких сторонних скриптов и шрифтов из сети:** Manrope собирается в бандл.
- **XSS:** пользовательские строки вставляются через `textContent`/TextNode. `innerHTML` используется только для статических шаблонов и иконок.
- **CryptoKey:** non-extractable, хранится в IndexedDB с привязкой к origin. Очистка данных сайта удаляет ключ без возможности восстановления.
- **Память:** content key и plaintext-байты очищаются после использования. Строки JS собрать невозможно; это ограничение среды.
- **Ошибки:** в UI не выводятся stack trace и внутренние детали; пользователю показывается понятное сообщение.

### CSP и GitHub Pages

CSP встраивается в `index.html` при production-сборке. GitHub Pages отдаёт статические файлы, поэтому заголовки задать нельзя; meta-CSP — компромисс. При переезде на собственный хостинг рекомендуется продублировать политику HTTP-заголовком и добавить `frame-ancestors 'none'`.

## 7. Проверки

`npm test` запускает 19 тестов.

Криптография (12):

- неэкстрагируемость приватного ключа;
- round-trip для нескольких устройств;
- 12 независимых генераций ключей (регрессия на вывод публичного ключа);
- отдельный конверт на устройство;
- отсутствие plaintext в ciphertext;
- отказ устройству без конверта;
- отказ при неверном ключе отправителя;
- отказ при изменённом ciphertext;
- отказ при изменённом AAD;
- отказ при переигровке конверта под другим `device_id`;
- отказ при неподдерживаемой версии;
- свежий content key на каждое сообщение;
- отказ на пустой текст и пустой список получателей.

Backend (7, PGlite — настоящий PostgreSQL, скомпилированный в WASM):

- миграции применяются по порядку без ошибок;
- триггер создаёт профили, первый пользователь становится owner, приглашение активирует аккаунт;
- bootstrap-миграция создаёт профили для существовавших `auth.users`, назначает owner и идемпотентна;
- `register_device` работает через RPC, а прямые записи в таблицы запрещены;
- `send_message` сохраняет конверты только для активных устройств активных участников и идемпотентен по `client_message_id`;
- RLS не отдаёт чужие сообщения, конверты и профили; заблокированный профиль теряет чтение и доступ к RPC;
- `get_conversation_devices` возвращает статус профиля и устройства отозванных устройств для истории.

Тесты не заменяют проверку hosted Supabase: Auth, Realtime, Dashboard-настройки и RLS под реальным JWT нужно проверить на проекте.

## 8. Известные ограничения

1. Нет recovery kit и восстановления после потери устройств.
2. Нет forward secrecy / post-compromise security.
3. Нет key transparency / safety numbers / QR-верификации ключей.
4. Отзыв устройства не завершает украденную сессию.
5. Нет MFA.
6. Нет автоматических тестов Auth/Realtime на hosted Supabase; backend-тесты покрывают миграции, RLS и RPC на PGlite.
7. Нет ограничения на смену публичного ключа устройства в пределах активной сессии.
8. Нет защиты от вредоносного оператора БД (см. модель угроз).
9. Нет вложений, стикеров и push в M1.
10. Нет независимого аудита.
